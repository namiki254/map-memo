# memop

好きな画像を「地図」として使い，その上にピンを立てて情報をみんなで書き込めるWebアプリ．ハッカソン（2026年8月）の制作物．

## 何を作るのか

普通の地図アプリと違うのは，**地図が現実の地図に限られない**ことです．ユーザーが好きな画像をアップロードすれば，それがそのまま「地図」になります．

- 現実世界の地図 → おすすめスポット，旅行情報，思い出
- テーマパークのマップ → アトラクション情報，写真スポット
- ゲームのマップ → アイテム，敵，攻略情報，思い出
- 大学や施設のマップ → 設備やおすすめの場所

つまり「好きな画像上の場所に情報を紐付け，複数人で共有できるサービス」です．

## MVP（まずここまで作る）

1. マップ一覧を表示
2. 新しいマップを作成
3. マップ用画像をアップロード
4. マップ画像を表示
5. 画像上をクリックしてピンを設置
6. ピンにタイトル・文章を書く
7. ピンをデータベースへ保存
8. 保存されたピンを他のユーザーも閲覧
9. マップごとのURLで共有

### 余裕があれば

ピンの編集・削除，ピンの種類やアイコン変更，カテゴリーやレイヤー，検索，ユーザー認証，共同編集の強化，マップのフォーク，更新履歴，リアクション．

期限内に完成しない可能性が出たら，上の「余裕があれば」は迷わず後回しにします．過剰設計は避けます．「将来的には必要」でも，MVPに不要なら実装しません．

優先順位は上から順に，**1週間で完成する / デモで正常に動く / 5人で作業分担できる / このアプリ独自の体験が伝わる / UIや完成度 / 追加機能 / 技術的な高度さ** です．

## 技術構成

- フロントエンド：React
- 開発環境：Vite
- 言語：JavaScript
- データベース：Supabase（PostgreSQL）
- 画像保存：Supabase Storage
- 認証：現時点では実装しない（必要になったら Supabase Auth を検討）
- ホスティング：Vercel
- ソースコード管理：Git / GitHub
- エディタ：VS Code 推奨

**バックエンドのサーバーは作りません．** Express などの独自APIサーバーは不要です．React から Supabase の JavaScript SDK を使って，ブラウザから直接データベースとStorageにアクセスします．

```
React + Vite
     ↓
  Supabase
  ├── PostgreSQL
  └── Storage
```

Node.js はバックエンドとしては使いません．ただし Vite と npm を動かすために，各自のPCにインストールが必要です．**Node.js は 22系（LTS）**を使ってください．パッケージマネージャは npm に統一します．

## データ構造

テーブルは2つだけです．

### maps

| 列 | 説明 |
| --- | --- |
| id | マップのID |
| title | マップの名前 |
| description | 説明文 |
| image_url | Storageに保存した画像のURL |
| created_at | 作成日時 |

### pins

| 列 | 説明 |
| --- | --- |
| id | ピンのID |
| map_id | どのマップのピンか |
| x | 横位置（0〜1の割合） |
| y | 縦位置（0〜1の割合） |
| title | ピンのタイトル |
| content | ピンの本文 |
| pin_type | ピンの種類 |
| created_at | 作成日時 |

### 座標は「割合」で保存します

ここが一番大事な設計です．**ピクセル座標ではなく，画像に対する割合（0〜1）で保存します．**

たとえば `x = 0.35, y = 0.62` なら「画像の左から35%，上から62%の位置」という意味です．

こうしておくと，画面サイズや画像の表示サイズが変わっても，ピンが必ず同じ場所に表示されます．ピクセルで保存すると，スマホで見たときにピンが全部ずれます．

### 画像はデータベースに入れません

アップロードされた画像は Supabase Storage に保存し，その **URLだけ** を `maps.image_url` に入れます．画像そのものをデータベースに入れてはいけません．

Storageのバケット名は `map-images` です．

### created_by は作りません

ユーザー認証を実装しないため，「誰が作ったか」の列は現時点では不要です．

## 地図の表示方法（未確定）

**ここはまだ決まっていません．** 現時点では2つの選択肢を残しています．

### 案1：ライブラリを使わない（MVPはこちらで足りる）

MVPでやることは「アップロードした画像を表示して，クリックした場所にピンを置く」だけです．これは `img` タグと，クリック位置を割合に直す計算だけで作れます．地図ライブラリは要りません．

計算は数行で済みます．

```js
const rect = e.currentTarget.getBoundingClientRect();
const x = (e.clientX - rect.left) / rect.width;   // 0〜1
const y = (e.clientY - rect.top) / rect.height;   // 0〜1
```

ピンを表示するときは，割合をそのままCSSのパーセントにします．

```jsx
<div style={{ left: `${pin.x * 100}%`, top: `${pin.y * 100}%` }} />
```

学ぶことが少なく，詰まる場所もほぼありません．**まずはこれで作ります．**

### 案2：Leaflet を入れる

拡大縮小してドラッグで動かせる地図にしたい場合や，現実の世界地図をスクロールして使いたい場合は Leaflet を導入します．

Leaflet は緯度経度の地図と1枚の画像を同じ仕組みで扱えます（画像を扱うときは `L.CRS.Simple` を指定します）．そのため，現実の地図とアップロード画像を1つのコンポーネントで両対応できます．

導入する場合の注意点を先に挙げておきます．

- Leaflet の座標系（CRS）は地図を作るときにしか指定できません．現実の地図と画像地図を切り替えるときは，`MapContainer` に `key` を渡して丸ごと作り直す必要があります．知らないと半日溶けます
- CSSの読み込み（`import "leaflet/dist/leaflet.css"`）を忘れると表示が崩れます
- 地図を置く要素に高さを指定しないと，何も表示されません
- 既定のピン画像がビルドと噛み合わず表示されないので，アイコンの設定が別途必要です

**判断の期限は，MVPの画像表示が動いてからで構いません．** 先に案1で動くものを作り，拡大縮小が本当に必要だと分かってから案2を検討します．最初からLeafletを入れると，覚えることが増えて手が止まります．

# 開発ルール

5人で1つのリポジトリを触ります．**このルールを守らないと，他の人の作業が消えます．** 面倒でも必ず通してください．

流れは常にこの順番です．

**Issueを作る → ブランチを作る → 作業する → PRを作る → Discordで報告 → レビュー → マージ**

## 1. Issueを作る

作業を始める前に，必ずIssueを立てます．「何をやるか」をチーム全員が見える場所に書くためです．

GitHubのリポジトリページ上部の **Issues** タブ → 右の **New issue** から作成します．

本文はこの形式で書いてください．

```markdown
## 概要
ピンをクリックしたときに詳細を表示するパネルを作る．

## 対象
- [ ] パネルのUI作成
- [ ] ピンのタイトル・本文の表示
- [ ] 閉じるボタン

## 備考
マップ表示（#3）ができてから着手する
```

`- [ ]` はチェックボックスになります．作業が進んだらチェックを付けると，進捗が他の人から見えます．

作成すると **Issue番号**（`#12` のような数字）が付きます．この番号を次の手順で使います．

## 2. ブランチを作る

**`main` ブランチで直接作業してはいけません．** 必ず自分専用のブランチを作ります．

ブランチ名はこの形式に統一します．

```
feature/#<Issue番号>-<英語のわかりやすい名前>
```

例：

```
feature/#12-pin-detail-panel
feature/#7-image-upload
feature/#3-map-list
```

英語部分は小文字とハイフンだけを使います．スペースや日本語は入れません．

### VS Codeでの操作

1. 画面左下に現在のブランチ名（最初は `main`）が表示されています．ここをクリック
2. 「新しいブランチの作成」を選ぶ
3. 上のルールに沿った名前を入力してEnter
4. 左下の表示が新しいブランチ名に変わればOK

### コマンドでの操作

```bash
git switch main
```

これは「mainブランチに移動する」コマンドです．**新しいブランチは必ず最新のmainから作ります．** 古い状態から作ると，後で他の人の変更とぶつかります．

```bash
git pull
```

これは「GitHub上の最新の状態を自分のPCに取り込む」コマンドです．他の人がマージした変更が反映されます．**ブランチを作る前に必ず実行してください．**

```bash
git switch -c feature/#12-pin-detail-panel
```

これは「新しいブランチを作って，そこに移動する」コマンドです．`-c` は create の意味です．実行すると，以降の変更はこのブランチだけに記録され，mainには影響しません．

## 3. 作業してコミットする

コミットは「ここまでの変更に名前を付けて記録する」操作です．こまめに行ってください．1日1回ではなく，**キリのいいところで毎回**です．

### VS Codeでの操作

1. 左のアイコン列から「ソース管理」（枝分かれのマーク）を開く
2. 変更したファイルの一覧が出るので，`+` を押してステージに追加する
3. 上のメッセージ欄にコミットメッセージを書く
4. 「コミット」ボタンを押す

### コマンドでの操作

```bash
git add -A
```

これは「変更したファイルを全部，記録の対象に加える」コマンドです．

```bash
git commit -m "feat: ピン詳細パネルの土台を追加"
```

これは「加えた変更を記録する」コマンドです．`-m` の後ろがメッセージです．

コミットメッセージは先頭に種類を付けます．`feat:` が新機能，`fix:` がバグ修正，`style:` が見た目の調整，`refactor:` が動作を変えない整理，`docs:` がドキュメントです．

## 4. GitHubに送る

```bash
git push -u origin feature/#12-pin-detail-panel
```

これは「自分のPCの記録をGitHubに送る」コマンドです．`-u origin <ブランチ名>` は初回だけ必要で，2回目以降は `git push` だけで済みます．

VS Codeなら，コミット後に出てくる「変更の同期」または「Publish Branch」ボタンを押すだけです．

## 5. PR（プルリクエスト）を作る

PRは「このブランチの変更をmainに取り込んでください」という申請です．

GitHubのリポジトリページを開くと，pushしたブランチについて **Compare & pull request** という黄色いバーが出ます．そこから作成します．

### タイトル

```
feat: ピン詳細パネルを追加 (#12)
```

コミットメッセージと同じ種類の接頭辞を付け，最後に **対応するIssue番号** を書きます．

ブランチ名から自動で入る `Feature/#12 pin detail panel` のようなタイトルは，そのままにせず必ず書き直してください．

### 本文

変更した内容を箇条書きにします．

```markdown
- ピン詳細パネルのコンポーネントを追加
- ピンをクリックするとパネルが開くように変更
- 閉じるボタンを実装

close #12
```

最後の `close #12` を書いておくと，**マージされたときにIssueが自動で閉じます．** 書き忘れると手で閉じることになるので，必ず入れてください．

## 6. Discordで報告する

**PRを作ったら，必ずDiscordに報告してください．** 報告がないとレビューされず，いつまでもマージされません．

PRのURLと，何をしたのかを一言添えて投稿します．

```
PR出しました
https://github.com/namiki254/memop/pull/15
ピンの詳細パネルを追加しました．レビューお願いします．
```

## 7. レビューとマージ

**レビューは金田または並木が行います．**

問題がなければレビュアーがマージします．**自分でマージしないでください．**

修正が必要な場合はPRにコメントが付きます．同じブランチで修正してコミットしてpushすれば，PRの内容は自動で更新されます．新しくPRを作り直す必要はありません．

マージが終わったら，次の作業に移る前に必ずこれを実行します．

```bash
git switch main
```

```bash
git pull
```

これで自分のPCが最新の状態になります．**これを忘れて古いmainから次のブランチを作ると，コンフリクトの原因になります．**

## 困ったときは

**間違えてmainで作業してしまった．** まだコミットしていなければ，そのまま新しいブランチを作れば変更ごと移動します．コミット済みなら，Discordで相談してください．自力で戻そうとすると悪化しがちです．

**コンフリクトが出た．** 他の人と同じ場所を編集したときに起きます．自己判断で消さず，Discordで相談してください．

**よく分からなくなった．** 消したり戻したりする前に相談してください．作業内容が残っていれば，たいていの状況は復旧できます．

## 開発上の注意

パッケージを追加したらDiscordで共有してください．他の人は `git pull` の後に `npm install` が必要になります．

`package-lock.json` は必ずコミットします．

`.env.local` はコミットしません．`.gitignore` で除外済みです．

**このリポジトリは公開されています．** コミットした内容は誰でも読めます．Supabase の secret キー（`sb_secret_` で始まるもの）は絶対にコミットしないでください．クライアントで使うのは publishable キー（`sb_publishable_` で始まるもの）だけです．

**Supabase は1週間アクセスがないとプロジェクトが自動停止します．** お盆期間中，週1回は誰かが開いてください．

Windows と Mac が混在しています．シェルスクリプトやパス区切り文字に依存した処理は書かないでください．
